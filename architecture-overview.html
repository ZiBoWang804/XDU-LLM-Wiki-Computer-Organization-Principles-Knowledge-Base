Knowledge Base Only

《计算机组成原理》知识库本体方案

这份方案不再讨论外围实现细节，只定义一件事： 这门课的知识库本体应该长什么样。 这里先只讨论知识库本体本身。

md-first 知识点中心 资料先读懂再入库 复杂图像单独解释

这份方案只管本体

不再写系统架构，不再写平台分层，只回答知识库里到底应该存什么。

最小单元只有一个

核心不是题目、方法、chunk、数据库记录，而是 知识点。

先不讨论外层能力

作业解答、组卷、批改、答疑先全部拿掉，这版只确立知识库自身。

1. 知识库里到底存什么

知识库本体只保留五类长期有价值的 Markdown 文件。

资料整理稿 每份教材、PPT、笔记、作业、试卷先被整理成一份可读 Markdown 稿，说明这份资料讲了什么、哪些页重要、能抽出哪些知识点、哪些地方有问题。
知识点页 这是核心资产。后面真正被反复调用的，不是整份课件，而是单个知识点页。
复杂图像解读页 对复杂图、结构图、表格、时序图、手写页单独保存解释稿，不把“识别出一点字”误当作“已经入库”。
勘误页 原始资料有错时，单独记录错点、修正依据和受影响知识点。
分歧页 多份资料说法不一致时，单独记录冲突和当前采用依据，不偷偷抹平。
这里的层次要固定：知识点页是规范层，资料整理稿是证据层。 默认先读知识点页；只有知识点页不够时，再顺着出处回读资料整理稿片段。

2. 为什么最小单元必须是知识点

因为知识点最稳定

题目会变，出题方式会变，检索方式会变，但“什么是流水线相关冲突”“什么是 8086 寻址方式”这种知识点本身是稳定的。

因为知识点最适合复用

无论外层以后怎么变化，课程内容最终都要回到知识点维度。

方法不是长期主资产。方法只是运行时把若干知识点组合起来后形成的临时结果。

3. 一个知识点页应该是什么样

知识点页不需要花哨，只需要后续好用、可引用、可追溯。

--- id: KP-C04-ISA-001 title: 8086 寻址方式 aliases: - 8086 地址表示方式 chapter: 第4章 指令系统 topic: 8086 type: mechanism source_refs: - 资料/课件/指令系统4--Spring.2024.pdf#p12 prerequisites: - KP-C04-ISA-000 related_points: - KP-C04-ISA-003 contrast_with: - KP-C04-ISA-004 updated: 2026-05-20 --- ## 定义 ## 课程资料中的表述 ## 结构 / 规则 / 公式 ## 易混点 / 易错点 ## 常见关联场景 ## 相关知识点 ## 出处

重点不在于元数据有多复杂，而在于这页单独拿出来就能懂，后续整理时能稳定复用。

关系类型只保留少量高价值项 推荐至少维护 `prerequisites`、`related_points`、`contrast_with`、`same_topic` 和 `source_refs`。
正文里维护正向链接 在正文里用 `[[知识点名]]` 明确写出这页主动链接到哪些知识点。
反向链接自动得到 不人工双写。反向链接由 Obsidian backlinks 或索引生成阶段自动反推。
只维护一边关系 例如 A 写 `prerequisites -> B`，不要再去 B 手写 `required_by -> A`。
这就是 Karpathy 式“双向链接网络”在这里的实现：页面显式出链，工具或索引层自动回推入链。

4. 原始资料怎样变成知识库

这里先区分两件事：本体结构决定最后存什么，入库工作流决定资料怎么进去。你图里的那条流程，可以保留为标准入库执行流。

1. 用户把文件放入 raw/buffer/ 2. pipeline.py 自动执行：哈希计算 -> 重复检测 3. 调用 MinerU（PDF）或 MarkItDown（PPT/Word）提取内容 4. 对命中的复杂页面调用 Vision LLM，生成图像解读草稿 5. LLM 复核表格提取精度 6. 分类移动到 raw/archive/，更新 manifest 7. LLM 编译：生成资料整理稿 + 知识点页 8. 冲突检测 -> 勘误检测 -> 更新目录/索引 -> 记录 log

这条流可以保留，但第 4 步只是执行动作；复杂页的触发条件和最终产物，要在知识库正文里单独说明。第 7 步的落点也要固定成当前知识库本体目录，而不是再额外造一套并行中心。

先保留原资料 教材、PPT、笔记、作业、试卷、图片、扫描件都先作为来源保留，不直接当知识库。
再形成资料整理稿 每份资料先被读懂，整理成一份可读的 Markdown 稿，而不是仅仅抽出文字。
复杂页单独解释 对复杂图、模糊图表、手写页、时序图、电路图单独形成解释页。
最后才抽知识点 真正进入主库的不是整份资料，而是从整理稿中抽出的知识点页。
发现错误或冲突时单独记录 不把错误或矛盾直接揉进主知识点页，而是分流到勘误页和分歧页。

5. 分层 index 如何避免全量读取

库变大后，不能让模型一上来就读完整个知识点目录，所以 `index.md` 应该是一组分层入口，而不是一个总表。

总索引 `知识库/index.md` 只负责最粗路由：章节入口、专题入口、继续往下读的方向。
章节索引 `章节/.../index.md` 只回答这一章有哪些专题、核心知识点和前置知识。
专题索引 `专题/.../index.md` 负责列出该专题下的知识点、易混点和强关联点。
正文只读少量页 模型按“总索引 -> 章节/专题索引 -> 少量知识点正文”的顺序收缩范围。
知识库/ ├─ index.md ├─ 章节/ │ ├─ 第3章-存储系统/ │ │ ├─ index.md │ │ └─ Cache/ │ │ ├─ index.md │ │ ├─ KP-C03-CACHE-001-局部性原理.md │ │ ├─ KP-C03-CACHE-002-直接映射地址划分.md │ │ └─ KP-C03-CACHE-003-组相联映射.md ├─ 专题/ │ ├─ Cache/index.md │ ├─ 流水线/index.md │ └─ 8086/index.md

注意：知识点正文只存一份，章节索引和专题索引只负责指向它。

6. 对低质量资料采取什么原则

核心原则只有一句： 不是识别出字就算入库，而是真正读懂并整理出来才算进入知识库。

不是所有图片都要重点处理

封面、目录、普通标题页不值得重解释，真正需要重点处理的是高信息密度、结构复杂、OCR 破碎但内容关键的页面。

允许保留不确定

看不清的地方可以明确写“哪部分确定、哪部分不确定”，知识库不怕不确定，怕的是把错的东西写成对的。

7. 知识库本体的边界

这版先明确哪些东西不并入知识库本体：

  • 个人用户记忆
  • 作业解答逻辑
  • 批改逻辑
  • 组卷逻辑
  • 答疑逻辑
  • 展示界面
  • 检索实现
这些以后都可以接在知识库外面，但现在先不纳入本体。
与本体相邻的个人演化层 你的理解、类比、追问、替代解法、待确认质疑，不直接写进知识点页，而是先进入个人演化层。
默认保存规则 先记到个人演化层，挂到对应知识点，再决定是否验证通过并升级回知识点页、勘误页或分歧页。
演化层的最少类型 建议至少区分 `insight`、`analogy`、`alternative_solution`、`question`、`challenge`。
回答时分层展示 以后回答问题时，先给“课程规范内容”和“依据出处”，再单独附上“你的个人理解 / 类比 / 注意点”，不把二者混写。
个人演化/ └─ users/ └─ <user-id>/ ├─ index.md ├─ 理解笔记/ ├─ 个人类比/ ├─ 个人解法/ ├─ 问题追问/ └─ 待确认质疑/

两个基础模板： personal-insight-template.md 和 challenge-note-template.md

如果后续接入题目层和解答层，建议现在就固定知识点关联字段： `tested_points / used_points`，并允许直接扩展为 `tested_points_primary / tested_points_secondary / used_points_core / used_points_support`。 这些字段都应指向稳定的知识点 `id`。

8. 最小目录骨架

知识库/ ├─ 资料整理稿/ │ ├─ 教材/ │ ├─ 课件/ │ ├─ 笔记/ │ ├─ 作业/ │ └─ 试卷/ ├─ 知识点/ ├─ 图像解读/ ├─ 勘误/ ├─ 分歧/ └─ 目录.md

这已经足够表达知识库本体，不需要先把目录扩得很大。

9. Markdown、Obsidian、Codex 的角色

Markdown 是唯一主库 真正长期保存的知识资产都应落在本地 `.md` 文件里。
Obsidian 是人用界面层 负责浏览、双向链接、局部图谱、手动补充和审核。
Codex 是智能执行层 负责入库、抽取、解释复杂图像、生成索引、读取三层知识并组织输出。
关系固定为：Markdown 是主库，Obsidian 和 Codex 围绕它工作，而不是共同接管知识库。

10. 规则约束模块

除了目录、模板和入库流程之外，这套知识库还必须有一份面向大模型的规则约束文件。

它不存知识 它不负责保存课程内容，而是负责约束模型怎么读、怎么写、怎么升级、怎么回答。
它约束边界 明确哪些内容属于规范层，哪些属于证据层，哪些只能先进入个人演化层。
它统一模型行为 规定读取顺序、写回规则、关系维护方式、勘误和分歧处理方式、回答分层方式。

本仓库用 CODEX.md 承担这个角色。这里把它作为当前 Codex 驱动知识库的规则约束文件，但它仍然服务于所有 LLM / Agent 的统一操作宪章。

11. 什么不属于这份方案

为了防止再次跑偏，下面这些故意不写进知识库本体方案：

  • 外围实现怎么安排
  • 检索细节怎么处理
  • 调用细节怎么组织
  • 展示细节怎么呈现
  • 模型分工怎么微调
这些以后都可以加，但它们不决定知识库本体。真正决定本体的只有三件事：资料怎么被读懂、知识点怎么被写成 md、后面的能力怎么围绕这些知识点工作。

12. 最后的定句

这次要搭建的，不是一个外壳，而是 一套以知识点 Markdown 页为核心、以资料整理稿为来源、以复杂图像解释页为补充、以勘误和分歧记录为保障的《计算机组成原理》课程知识库。
