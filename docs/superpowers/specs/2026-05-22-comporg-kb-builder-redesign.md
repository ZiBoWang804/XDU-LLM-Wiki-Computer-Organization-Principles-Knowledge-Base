# comporg-kb-builder 重构设计

## 1. 重构结论

旧版 `comporg-kb-builder` 不适合原样保留，但其职责必须保留并重写。

结论拆分为三句：

1. **废弃旧实现路线**
   - 旧 skill 当前依赖 `comporg_agents`、`run_comporg.py`、`sqlite`、`wiki/content/maps` 等运行时产物。
   - 当前仓库中这些依赖已不成立，skill 实际上不可运行。

2. **保留角色职责**
   - 本地资料入库
   - PDF / Office 材料转换
   - 复杂图像理解
   - 图谱 / 思维导图派生
   - 入库前审核与冲突治理

3. **改写为 md-first 基座技能**
   - 以 `知识库/**/*.md` 为唯一主库
   - 以 `MinerU + 主模型审核 + 图像子 agent + doctor 复检` 为新主流程

## 2. 新版定位

新版 `comporg-kb-builder` 不是“旧运行时知识库 rebuild 工具”，而是：

**一个把本地资料加工、审核、清洗、补强后，再准许沉淀到 Markdown 主知识库，并可选生成派生产物的知识库基座 skill。**

它负责：

- 接收本地资料
- 调用 `MinerU / markitdown` 做类型适配
- 对抽取结果做主模型准入审核
- 必要时启动图像理解子 agent
- 组织 `资料整理稿 / 图像解读 / 题型层扩展页 / 索引 / 知识点沉淀候选`
- 在用户要求时生成图谱和思维导图

它不再默认负责：

- 构建 sqlite 数据库
- 驱动旧 `comporg_agents`
- 依赖旧 `wiki/content/maps` 派生运行时

## 3. 最高优先级约束

任何入库、清洗、图像理解、索引更新、知识点沉淀，都必须先遵守：

- `D:\wzb\计算机组成原理\AGENTS.md`
- `D:\wzb\计算机组成原理\CODEX.md`

这不只是“回答时参考”，而是**入库流程前置约束**。

硬规则：

1. 主线程入库前必须先读取 `AGENTS.md` 与 `CODEX.md`
2. 所有子代理也受这两份规则约束
3. 任何脚本产物都不能绕过这两份规则直接入库

## 4. 工具角色分工

新版工作流中各工具角色固定如下：

- `Markdown`
  - 知识库主资产
- `PyYAML`
  - frontmatter、结构元数据、规则文件辅助
- `markitdown`
  - Word / PPT / Office 资料转 Markdown
- `MinerU`
  - PDF 主抽取路线
- `Obsidian`
  - 人用界面层
- `Codex 主模型`
  - 准入审核、结构清洗、知识正确性检查、统一入库裁决
- `Codex 子代理`
  - 并行处理某类资料、复杂图像理解、特定类型审核
- `comporg-doctor`
  - 入库后复检与治理

## 5. PDF 主路线

PDF 主路线固定为：

- `MinerU`

不再把通用 OCR 写成默认主链。

规则：

1. PDF / 扫描资料首先走 `MinerU`
2. 仅在极特殊兜底场景下，才允许退回本地 OCR 路线
3. 兜底 OCR 不作为默认主流程写入新版 skill

## 6. 资料处理三层结构

新版基座必须引入“准入缓冲层”，避免抽取结果直接污染主库。

推荐三层：

### 6.1 `raw_extract`

用途：

- 保存 `MinerU / markitdown` 的原始抽取结果
- 允许存在：
  - 乱码
  - 结构噪声
  - 公式 / 表格错位
  - 未修复图像占位

特点：

- 只做原始痕迹保留
- 不作为日常主读取层

### 6.2 `reviewed_draft`

用途：

- 作为入库审核中的缓冲稿
- 由主模型完成：
  - 清洗
  - 语义连贯性检查
  - 错误片段剔除或挂起
  - 图像锚点插入

特点：

- 面向审核，不直接等于正式主库

### 6.3 `accepted_kb`

用途：

- 通过审核后，正式进入：
  - `资料整理稿`
  - `图像解读`
  - 相关索引页
  - 后续知识点沉淀候选

特点：

- 只有通过审核才能进入这一层

## 7. 准入审核机制

这是新版 `comporg-kb-builder` 的核心。

任何要进入知识库主库的 Markdown，都必须先经过主模型审核。

### 7.1 审核项

至少检查：

1. 是否有乱码
2. 是否语义错乱
3. 是否关键内容缺失
4. 是否存在明显知识性错误
5. 是否与客观规律明显矛盾
6. 是否与本地已有高可信知识冲突
7. 是否达到“可入库”标准
8. 是否需要拆分到不同层：
   - 资料整理稿
   - 图像解读
   - 勘误 / 分歧候选
   - 个人演化候选

### 7.2 审核结论

固定三类：

- `pass`
- `repair_then_pass`
- `hold_for_review`

### 7.3 最高原则

**先审核，后入库。**

脚本不能直接把抽取稿机械塞进正式主库。

## 7.4 二段式入库规则

这是新版基座的重要防污染规则。

资料通过审核后，**只能先进入证据层**；  
题型页、作答母版、视觉索引、知识点页、专题页等规范/半规范层内容，必须经过第二步知识沉淀后才能更新。

### 第一阶段：证据层准入

审核通过后，允许先进入：

- `资料整理稿`
- `图像解读`
- 必要的 `勘误候选`
- 必要的 `分歧候选`

此阶段的目标是：

- 保存稳定可读的资料整理结果
- 保留图像解释与原图追溯
- 不把抽取结果过早推入规范层

### 第二阶段：规范层沉淀

只有在主模型完成二次沉淀判断后，才允许更新：

- `题型页`
- `题型作答母版`
- `题型视觉索引`
- `知识点页`
- `专题页`
- `反向题型索引`

### 可升格到知识点页的条件

- 结论稳定
- 术语清楚
- 与教材口径一致，或可明确标注为补充说明
- 不只是单题语境下成立
- 可长期复用

### 可升格到题型层扩展页的条件

- 题型足够高频
- 解法骨架稳定
- 表达方式值得复用
- 题目图 / 答案图 / 版式特征具有代表性

### 只保留在证据层的情况

- 仍存在 OCR / 图像歧义
- 只是单次题目特例
- 还没抽象出稳定模板
- 可能与其他资料冲突

## 8. 复杂图像理解工作流

这部分是新版 skill 的关键升级点。

### 8.1 触发条件

主模型检查 `MinerU` 结果时，若发现以下任一情况，立即触发图像理解子 agent：

- 语义不通
- 明显乱码
- 大段空洞
- 关键图表被丢失
- 图片类页 / 图像型 PDF
- 表格结构错乱
- 电路图 / 数据通路图 / 结构图 / 手写图

### 8.2 子 agent 模型

复杂图像理解子 agent 默认使用：

- `gpt-5.4`

### 8.3 子 agent 输出

输出两类结果：

1. 适合后续大模型检索和理解的结构化说明
2. 尽量完整保留信息的：
   - 表格转录
   - 图示解读
   - 关键字段整理

### 8.4 写回位置

复杂图像理解结果默认**不直接写进知识点正文**。

默认写回到：

- `知识库/图像解读/`

同时在对应 `资料整理稿` 中保留图像锚点。

## 9. 资料整理稿与图像解读分离

你已经明确要求这一部分重新设计，新的规则如下。

### 9.1 资料整理稿

资料整理稿面向：

- 人阅读
- 主模型日常检索

它必须保持干净，不允许保留：

- MinerU 乱码
- 语义不清文字片段
- 明显错误识别结果
- 图像解读正文

它可以保留：

- 清洗后的正文
- 精确图像锚点
- 指向图像解读页的链接
- 必要的“此处见图像解读”提示

### 9.2 图像解读

图像解读单独保存：

- 大模型对复杂图像的解释
- 表格重建
- 图示结构说明
- 原图追溯信息

### 9.3 图像锚点要求

资料整理稿中的每个图像锚点至少要记录：

- `source_file`
- `page_no`
- `figure_id`
- `image_path`
- `figure_type`
- `figure_explained_in`
- 必要时 `bbox` 或区域描述

### 9.4 展示方式

优先方案：

- 在资料整理稿里内嵌缩略图
- 同时链接到图像解读页

这样既方便人读，也便于追溯。

## 9.5 并入题型层，而不是新开视觉主层

与题目和答案风格强相关的视觉证据，不再新开独立“题型视觉索引主层”。

而是默认并入题型层内部，采用以下组织方式：

- `QT-xxx.md`
  - 题型主页面
- `QT-xxx-作答母版.md`
  - 该题型的标准书写骨架、句式和步骤展开方式
- `QT-xxx-视觉索引.md`
  - 原题图片缩略索引、标准答案图片缩略索引、版式特征、图片解读索引
- `题型/assets/QT-xxx/`
  - 缩略图或原图引用资源

原则：

- 仍然属于题型层
- 不另起独立平行主层
- 题型主页面保持简洁
- 视觉模板与作答母版作为题型扩展页存在

## 9.6 题型视觉证据的入库目标

当资料中出现高价值题目图片、答案图片、课件版式示例时，应优先沉淀为：

1. 题型主页面的正向入口
2. 题型作答母版页
3. 题型视觉索引页
4. 必要时关联到图像解读页

而不是把整段视觉解读塞进知识点正文。

## 10. 反向索引与追溯

图像解读必须建立可追溯结构。

至少支持：

- 按资料索引
- 按章节索引
- 按知识点索引
- 按 `figure_id` 直达

并保留原图路径，便于：

- 后续人工修复
- 错误追踪
- doctor 复检

## 11. 并行入库策略

新版应支持并行处理，但并行的是“转换与审核前处理”，不是直接并行写正式库。

### 11.1 并行子代理分工

可并行的 lane 包括：

1. `PDF-text lane`
   - 处理文本型 PDF
   - `MinerU` 抽取
   - 初步清洗

2. `PDF-vision lane`
   - 处理图片型 PDF、复杂表格、复杂图
   - 调用复杂图像理解子 agent

3. `PPT lane`
   - `markitdown`
   - 按页整理结构

4. `Word lane`
   - `markitdown`
   - 清洗标题、正文、表格

5. `Notes / misc lane`
   - 处理 Markdown / TXT / 零散笔记

### 11.2 主线程职责

主线程负责：

- 统一分发
- 汇总各子代理结果
- 执行最终准入审核
- 决定哪些内容正式入库
- 更新索引与反向索引

### 11.3 禁止事项

子代理不应直接改正式主库核心页面，避免：

- 风格不统一
- 分层混写
- 并发冲突

## 12. doctor 挂钩

新版 `comporg-kb-builder` 应与 `comporg-doctor` 协同。

### 12.1 触发条件

发现以下情况时，生成：

- `doctor_hook_required`

候选：

- 资料冲突
- OCR / 抽取污染
- 图像解释与文本冲突
- 索引不一致
- 分层违规
- 入库后抽检失败

### 12.2 doctor 负责内容

`comporg-doctor` 负责：

- 冲突检查
- 结构检查
- 模板偏差检查
- 链接 / 索引检查
- 证据污染检查
- 规范层 / 演化层混写检查

## 13. 图谱与思维导图

这两者不是默认主流程。

规则：

- 入库完成后，询问用户是否生成
- 用户拒绝则不生成
- 用户同意才生成

也就是说：

- 默认不生成
- 只在用户要求时生成

## 14. 新版工作流

新版 `comporg-kb-builder` 的推荐流程为：

1. 读取 `AGENTS.md`
2. 读取 `CODEX.md`
3. 判断资料类型
4. 分发给对应子代理做抽取 / 转换
5. 主模型检查 `raw_extract`
6. 必要时触发复杂图像子 agent
7. 形成 `reviewed_draft`
8. 将高价值题目图 / 答案图 / 课件版式特征挂入对应题型层扩展页候选
9. 执行准入审核
10. 审核通过后，正式写入：
   - 资料整理稿
   - 图像解读
   - 题型作答母版 / 视觉索引候选
   - 索引页
   - 后续知识点沉淀候选
11. 按需挂钩 `comporg-doctor`
12. 若用户要求，再生成图谱与思维导图

## 15. 旧版应废弃的内容

重写时应废弃：

- 对 `comporg_agents` 的硬依赖
- 对 `sqlite` 主索引的默认依赖
- 对 `wiki/content/maps/*.html` 的默认存在假设
- “先 rebuild 旧运行时再答题”的主流程

## 16. 可复用的内容

仍值得复用的脚本 / 思路包括：

- `scripts/ingest_materials.py`
  - 资料分类和格式接入思路
- `scripts/ingest_textbooks.py`
  - 教材入库思路
- `scripts/mineru_api_doctor.py`
  - MinerU 配置自检
- `docs/tooling/SETUP.md`
  - 工具角色说明

## 16.1 旧脚本的新地位：参考片段库

旧脚本不再作为新版基座的固定主流程。

新的处理原则是：

- 保留其中有价值的函数片段与用法
- 废除其“必须原样执行”的地位
- 每次入库由主模型根据本轮资料情况，自主决定是否：
  - 直接操作
  - 生成临时脚本
  - 改写旧函数片段
  - 组合多个片段

也就是说：

**脚本是参考，不是法条。**

## 16.2 允许的动态处理方式

对于不同类型、不同数量、不同质量的资料，主模型可根据需要选择：

1. 直接处理
2. 复用旧函数片段
3. 改写旧函数片段
4. 临时生成本轮专用脚本
5. 分发给并行子代理处理

但不允许：

- 机械套用旧脚本而跳过审核
- 把旧脚本当作不可修改的强制规则

## 16.3 必须保留的护栏

虽然实现方式可以动态变化，但必须满足以下护栏：

### 护栏 1：固定输出契约，不固定实现方式

无论采用哪种临时方案，最终产物都必须满足统一结构，例如：

- `raw-extract.md`
- `reviewed-draft.md`
- `images/`
- 图像锚点字段
- manifest / 索引基础结构

### 护栏 2：临时脚本不得直接写规范层

即使本轮临时生成脚本，它也只能负责：

- 抽取
- 清洗
- 生成 reviewed draft 候选
- 生成图像解读候选

不得直接改：

- `知识点页`
- `题型页`
- `专题页`

### 护栏 3：高风险动作必须留痕

例如：

- 替换乱码段
- 图像理解结果回写
- 表格重建
- 知识冲突判断

都必须保留痕迹，不能静默覆盖。

### 护栏 4：反复稳定的片段，才升级为正式参考

如果某种临时处理片段连续多次稳定有效，才考虑把它沉淀为新的参考片段。

## 16.4 参考片段库建议形态

不建议继续把旧脚本整体当作“入口脚本”保留。

更适合的形态是：

1. `scripts/_references/*.py`
   - 保留可复用函数片段
2. `docs/tooling/reference-patterns.md`
   - 记录这些片段的适用场景、用法和注意事项

这样后续主模型每次入库时：

- 先读规则
- 再看是否需要参考这些片段
- 决定是复用、改写还是临时生成

## 17. 一句话总结

新版 `comporg-kb-builder` 的核心使命是：

**以 MinerU 为 PDF 主路线，在 AGENTS.md 与 CODEX.md 约束下，通过主模型准入审核与复杂图像子 agent 补强，把本地资料高质量沉淀到 Markdown 主知识库，并仅在用户要求时生成图谱与思维导图。**
